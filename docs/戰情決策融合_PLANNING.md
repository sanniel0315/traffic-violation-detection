## 二、融合原則

1. **一件事只有一個入口。** 現在要看「我方現在建議什麼」有兩個地方，
   使用者得自己判斷該看哪個 —— 這是分頁切太細的代價。
2. **即時的留在前面，可稽核的收在後面。** 戰情是「掃一眼就知道現在怎樣」，
   決策盤是「要驗算時攤開來看」。兩者不是不同主題，是**同一主題的兩個深度**。
3. **不要為了融合把可稽核性砍掉。** 演算法規格與參數、影子比對、接管路線圖
   都是驗收要用的，只是不該跟即時畫面搶版面。

## 三、目標資訊架構

分頁從 8 個收斂到 6 個：

```
即時戰情（合併後）          燈態      影子可視化   設定   運作統計   驗收
├─ 建議動作 hero（閘門＋算式）                     ← 原 live hero，已改好
├─ 控制權現況（策略位元、EffectTime、模式碼）      ← 原 plan，橫向一列即可
├─ 上／下匝道兩欄（相機、車流、即時秒數）           ← 原 live
├─ 路口地圖燈態                                    ← 原 live
└─ 〔展開〕決策依據明細                            ← 原 plan 的其餘卡片
     ├─ 演算法規格與參數
     ├─ 影子決策比對
     └─ 接管路線圖
```

`device 設備狀態` 併入 `燈態`（都是控制器硬體層的東西），或維持獨立，
待使用者決定 —— 本文不預設。

**關鍵設計：〔展開〕預設收合。** 即時畫面保持乾淨，要驗算時才展開。
這樣既不失去可稽核性，也不會讓來賓被一堆數字淹沒。
