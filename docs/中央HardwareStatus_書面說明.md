# HardwareStatus 位元組順序不一致 — 實測報告與請求事項

**設備編號**：`SIG-N8-E-9-L-E-1`（國道8號新市交流道 東向）
**控制中心**：`control_center_id = 40`
**實測日期**：2026-09-09 12:13 ~ 14:29
**提出單位**：交通違規影像分析系統維運方
**協定依據**：TC3 通訊協定 4-21 / 4-22 / 4-36

---

## 一、主旨

本站控制器上傳的 `HardwareStatus`（`0F04` / `0FC1`，2-byte 無號整數），
在中央端被以**與我方相反的位元組順序**解析，導致：

1. 中央畫面顯示的告警名稱與控制器實際狀態**不符**；
2. 中央畫面的「硬體狀態」燈號與告警欄**不可能同時正確**。

謹以 16 個位元的逐位實測結果說明成因，並提出請求事項。

---

## 二、結論（先講結果）

**中央端解析到的位元編號 ＝ 我方送出的位元編號 ±8，十六位無一例外。**

亦即：同一個位元組，我方視為 bit8\~bit15（高位元組），中央端視為 bit0\~bit7。
這是 2-byte 欄位的位元組順序差異，非位元定義差異——**兩端的位元名稱表完全相同**
（詳見第五節）。

由此衍生一個**我方無法以任何送出值解決**的問題：
中央端的「控制器就緒」與「號誌驅動單元錯誤」讀取的是**同一個實體位元**（詳見第六節）。

---

## 三、實測方法

1. 我方於 `0F04` / `0FC1` 的 HardwareStatus 欄位（框內 offset 9\~10）
   逐次送出「僅單一位元為 1」的值，共 16 次。
2. 每次均確認該值**確實出現在通訊線路上**（保留原始碼框紀錄），
   再等中央端 `scmXMLData.xmL`（1 分鐘週期）更新**兩個週期**後讀取。
3. 讀取來源：
   `http://10.105.6.73/api/smg/r24a/device/scmXMLData.xmL` 的 `eq_hw_status`。
4. 燈號欄位不在該 XML 內，由現場人員直接觀看中央畫面回報。

全部 16 筆的送出時間、上線路時間、XML 時間與顯示結果均有逐筆紀錄，可供查驗。

將中央端顯示的名稱，與協定 4-36 位元表**同一編號**的名稱並列：

| bit3 | `看門狗計時器異常` | 看門狗計時器錯誤 | 一致 |
| bit4 | `電源異常` | 電源異常 | 一致 |

**16 個編號、16 個名稱全部吻合**；且中央端無告警名稱的兩格（bit8、bit14），
正是該表中**唯二非錯誤類**的兩項。

協定 4-36 載明「各位元為建議及參考內容，主辦機關可依需求修訂」。
惟由上表可知，**兩端並未各自修訂位元定義**——若曾修訂，16 個名稱不會全數一致。
故本案的歧異點僅在於：**該 2-byte 欄位的位元組順序**。

## 六、就緒燈號與 `SIGNAL_DRIVER_UNIT_ERROR` 讀取同一位元

中央畫面另有「硬體狀態」燈號，該欄位不在 `scmXMLData.xmL` 內，
由現場人員觀看畫面確認，三次實測結果：

| 我方送出 | 第一位元組 | 該位元組的 bit6 | 中央告警欄 | 中央硬體狀態燈號 |
|---|---|---|---|---|
| `0x4000` | `0x40` | **1** | `SIGNAL_DRIVER_UNIT_ERROR` | **正常（綠）** |
| `0x0040` | `0x00` | 0 | （空） | **異常（紅）** |
| `0x0400` | `0x04` | 0 | `計時器異常` | **異常（紅）** |

由第二、三列可知，燈號**與告警欄有無內容無關**（無告警時仍為紅、
有告警時亦為紅），其判準為**第一位元組的 bit6**。
而依第四節，該位元同時就是中央告警表的 bit6 `SIGNAL_DRIVER_UNIT_ERROR`。

因此：

- 該位元設為 **1** → 燈號正常，**但告警欄出現不存在的號誌驅動單元錯誤**；
- 該位元設為 **0** → 告警欄乾淨，**但燈號恆為異常**。

**兩者互斥，我方送出任何值皆無法同時滿足。** 送出 `0x4040` 亦無效——
告警欄僅取第一位元組，仍將顯示 `SIGNAL_DRIVER_UNIT_ERROR`。

## 七、我方採 big-endian 之依據

1. **協定 4-22** 定義 `HardwareStatus` 為 2-byte 無號整數。
2. **同協定其他 2-byte 欄位**（如 `5F03` 之 `StepSec`）我方以 big-endian 解讀，
   其正確性由現場步階倒數畫面逐秒佐證。
3. **bit14（控制器就緒）於運轉期間恆為 1。** 若依中央端讀法，等同本控制器
   連續十日持續回報「號誌驅動單元錯誤」，惟同期號誌運轉正常、無維修紀錄。
4. **bit13 與外部時相控制授權高度相關。** 與我方送出之 `5F10` 控制策略 bit4
   逐筆比對，45,843 筆樣本一致率 95.8%，不一致部分均可由回報週期延遲解釋。
   此相關性在相反的位元組順序下不存在。

## 八、目前造成的實際影響

| 中央端顯示 | 控制器實際狀態 |
|---|---|
| `記憶體異常` | 機箱門開啟（我方電子鎖門磁實測佐證） |
| `I/O unit error` | 外部時相控制進行中（當日下發全數為控制器接受） |
| `SIGNAL_DRIVER_UNIT_ERROR` | 控制器就緒（號誌運轉正常） |

我方曾嘗試兩種權宜上傳方式，兩者各有代價且**皆非正確解**：

| 上傳方式 | 中央硬體狀態燈號 | 中央告警欄 |
|---|---|---|
| 原值上傳（**現行**） | 正常 | 出現不存在的 `SIGNAL_DRIVER_UNIT_ERROR` |
| 位元組對調上傳 | 恆為異常 | 乾淨 |

現行採原值上傳（即完全依協定 4-22 之 big-endian 解讀送出，未做任何補償），
以確保燈號正確；告警欄之 `SIGNAL_DRIVER_UNIT_ERROR` 為中央端讀法所致，
**該項故障實際不存在**。

另我方將 bit13（外部時相控制進行中）遮蔽後上傳。該位元為狀態指示而非故障，
但在中央端被解析為 bit5 `I/O unit error` 並列入告警管理。
「由何方控制」之權威來源不受影響——中央以 `5F40` 查詢控制策略時，
我方均據實回覆含時相控制旗標之值。

## 九、請求事項

1. 請中央端將 `HardwareStatus`（`0F04` / `0FC1`）的解析統一為協定 4-22 所定之
   2-byte 無號整數（big-endian），使「硬體狀態燈號」與「告警名稱」兩條路徑
   採用相同的位元組順序。
2. 若中央端認定現行位元定義與協定 4-36 不同，請提供**正式的位元對照表**，
   我方將據以調整。
3. 中央端完成修正後請告知，我方將於同一時點解除權宜措施並共同驗證
   （驗證需同時檢視 `eq_hw_status` 與中央畫面燈號兩者，
   僅檢視 XML 會遺漏燈號路徑）。
