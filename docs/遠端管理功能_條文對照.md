## 二、八個被控制器拒收的查詢（要問廠商）

每則都是我方送出後控制器回 `0F81`。

**2026-09-09 已知的三則：**

```
送 5F4A FF 01   → AA BB 0A ... 0F 81 5F 4A 08 04 AA CC   ErrorCode=08
送 5F4B 08      → AA BB 0B ... 0F 81 5F 4B 08 03 AA CC   ErrorCode=08
送 5F5F 00      → 歷史 16 次全部 0F 81 ... ErrorCode=01
```

**🛑 2026-09-10 新增五則 —— 開啟「設定定期抄錄」第一輪就查出來的：**

```
09:08:50  送 5F43 → 0F 81 5F 43 08 00   ErrorCode=08   時相資料(時相排列)   條文 B
09:08:51  送 5F46 → 0F 81 5F 46 08 00   ErrorCode=08   一般日時段型態       條文 D
09:08:51  送 5F47 → 0F 81 5F 47 08 00   ErrorCode=08   特殊日時段型態       條文 D
09:08:51  送 5F49 → 0F 81 5F 49 08 00   ErrorCode=08   觸動控制組態         條文 F
08:59:40  送 5F42 → 0F 81 5F 42 08 00   ErrorCode=08   特殊日車道調撥       (非條文項)
```

🛑 **為什麼拖到現在才發現：我方從來沒送過這五支。**
   `5F43` / `5F46` / `5F47` / `5F49` 的「我方送出次數」都是 **0** ——
   號誌設定頁上看得到資料，是**側錄中央查詢時控制器的回報**存下來的，
   不是我方查到的。中央近 30 天只固定輪詢 4 支（`5F40` / `0F41` / `5F48`
   加下控 `5F10`），其餘只在 42.7 小時前的一次性盤點各出現 1~2 次。
   所以那些畫面上的資料是**舊快照**，而且我方一直沒有能力自己更新它。

🛑 **這直接改變 B / D / F 的認定。** 原本表上寫「✅ 已抄到」，是把
   「畫面上有資料」當成「查得到」—— 那是兩件事。現在實測是：
   **這台控制器不回這幾則查詢**，我方無法主動取得現況。
   在問到廠商之前，條文 B（時相排列）、D（時段型態）、F（觸動組態）的
   **查詢**同樣不可宣稱做得到。

🛑 `ErrorCode` 的確切語意**規範裡沒有對照表**。08 與 01 是不同的碼，
代表拒收的理由不同，不要一律當成「不支援」。要問廠商的兩件事：

1. 這八則是**韌體未實作**，還是**參數帶錯**？
   （新增的五則 `5F43`/`5F46`/`5F47`/`5F49`/`5F42` 都是**不帶參數**的純查詢，
   連可以帶錯的欄位都沒有 —— 這一點對「是不是參數問題」是很強的反證。）
   （`5F4A` 的 `SegmentType=FF` 依 schema 是「改用 WeekDay 查詢」的合法值；
   `5F4B` 的 `SegmentType=08` 在 8~14 的合法範圍內；
   `5F5F` 的 `PhaseOrder=0` 與 `5F03` 回報的 phase_order 一致。）
2. `ErrorCode` 01 / 08 各代表什麼？

在得到答案之前，條文 B 的時相排列查詢、D 的時段型態查詢、F 的觸動組態與
排程、H 的步階排列**都不能宣稱做得到** —— 那不是我方的介面問題，
是這台控制器不回。

🛑 **八則裡有七則是 `ErrorCode=08`，只有 `5F5F` 是 `01`。** 08 這麼集中，
   比較像「這個查詢族系整批未實作」而不是個別參數問題。但這仍是推論，
   規範沒有 ErrorCode 對照表，要廠商給正式說明。

### 定期抄錄會自動跳過它們

「設定定期抄錄」每輪送出前會先看歷史：這個查詢碼被拒收過就不再送。
實測第一輪送 13 則（其中 5 則被拒），第二輪就只送 9 則、**新增 NAK 0 筆**。
不會每天固定在線路上製造八筆 NAK。

## 三、J 的認定要講清楚

條文寫「設備可與網路上之中央電腦 NTP 伺服器自動校正系統時間」。

- **我方主機（Jetson）**：走系統 NTP，設定頁在「系統設定」。
- **號誌控制器**：TC3 沒有 NTP，我方以 `0F12` 設備日期時間－設定
  代行，預設每 60 分鐘檢查、差 2 秒以上才校正、超過 300 秒只告警不自動改。
  控制器時間來自 `0F42`→`0FC2`，時間基準是我方主機（其上游才是 NTP）。

🛑 所以嚴格講，控制器不是「自己對 NTP」，是「我方對 NTP、再把時間寫給控制器」。
   驗收時要說清楚是哪一種，不要讓人以為控制器直接連 NTP。

## 四、「設定」為什麼多數未實作

查詢與設定是兩件事。目前我方主動下傳的只有四種：
`5F10`（控制策略續約）、`5F1C`（時相步階變換）、`0F12`（校時）、`0F10`（重新啟動）。

其餘設定類（`5F13`~`5F1E`、`5F2F`）**寫得出來但沒有做介面**，原因是它們會
改動主管機關核定的時制內容 —— 要開放之前必須先確定：誰可以按、
按下去要不要覆核、以及改壞了怎麼還原。這是政策問題不是技術問題。

通用的「號控下傳」面板本來可以送這些碼（後端 `control/schemas` 已列出 98 則
命令與其欄位定義），但該面板 2026-09-08 依現場要求移除。

## 五、🛑 條文 E：`5F18` 不是被拒收，是**需要中央手動（bit3）**

2026-09-10 補正。本文件先前一度寫成「這台控制器拒收 `5F18`」——**那句是錯的**，
是因為只試了 `0x14`（路口手動＋時相控制）、`0x04`、`0x01` 三種策略就下了結論。

實測結果：

| 當下控制策略 | 送 `5F18 PlanID=37` | 之後 `5FC8` 回報的計畫 |
|---|---|---|
| `0x14` 路口手動＋時相控制（我方常態） | ❌ NAK ErrorCode=2 | 不變 |
| `0x04` 路口手動 | ❌ NAK ErrorCode=2 | 不變 |
| `0x01` 定時 | ❌ NAK ErrorCode=2 | 不變 |
| **`0x08` 中央手動（bit3）** | **✅ ACK** | **37** |
| `0x09` 定時＋中央手動 | ✅ ACK | 37 |
| `0x0C` 路口手動＋中央手動 | ✅ ACK | 37 |

**結論：`5F18` 只在控制策略含 bit3 中央手動時才被接受。** ErrorCode=2 是
「當下的控制權不允許這個動作」，不是不支援這個碼。

### ⚠ 與我方安全網的衝突（切換前一定要知道）

我方的降階安全網把「中央手動」視為**中央接管**，一進入就降到 **L2**、
停止演算法下控。所以走 `5F18` 切換計畫會是這個序列：

```
0x14 ──設 0x08 中央手動──> 安全網降 L2（演算法停）
     ──送 5F18──> ACK，計畫切換
     ──還原 0x14──> 安全網自動回 L0，演算法恢復
```

實測整段約 30 秒，還原後自動回 L0，**不需要人工復歸**。
但這段時間演算法確實沒有在控 —— 尖峰時段切換要把這點算進去。

🛑 任何切換腳本都必須把「還原 `0x14`」放在 `trap EXIT` 裡，
中斷或例外都要還原；把還原寫在最後一行是不夠的。

### `5F15`（寫時制計畫內容）**不需要**中央手動

原本預期 `5F15` 會跟 `5F18` 一樣要 bit3 —— **預測錯了**。
實測在常態 `0x14` 之下直接 ACK，並可用 `5F45` 查回來逐欄核對。
2026-09-10 就是用它把計畫 35/1/36/37 的分相1／分相2 綠燈對調，
每一則都走「組框 → 反解驗證 → prepare 預覽 → send → `5F45` 查回比對」，
沒有動過控制策略。

**所以要改時制內容走 `5F15`，不要為此切中央手動；只有「切換執行中的計畫」
才非走 `5F18` 不可。**
