## 協定：一組五則，兩條路

group = **設備日期、時間管理**

| 代碼 | 名稱 | 類別 | 頁 | 欄位 | 我方狀態 |
|---|---|---|---|---|---|
| `0F12` | 設備日期時間－設定 | 設定 | 4-23 | Year, Month, Day, Week, Hour, Min, Sec（各 1 byte） | 未送過 |
| `0F92` | 設備日期時間－設定回報 | 設定回報 | 4-25 | **SecDif（1）** | 未抄到 |
| `0F42` | 設備日期時間－查詢 | 查詢 | 4-26 | — | 已送 2 次 |
| `0FC2` | 設備日期時間－回報 | 查詢回報 | 4-27 | Year…Sec | 已抄到 2 筆 |
| `0F02` | 設備日期時間－主動回報 | 主動回報 | 4-28 | — | **全庫 0 筆** |

**① 寫入**：`0F12` → `0F92`。`0F92` 帶 **`SecDif`**，控制器會回報**校正前差了幾秒** ——
對時不是盲送，送完就有客觀偏差量可記錄。這正是監控時鐘漂移要用的數據。

**② 讀取**：`0F42` → `0FC2`（我方主動查），或 `0F02`（控制器主動推）。
`0F02` 全庫 0 筆 —— 這台控制器沒有在主動報時，或需要設定才會報。**待確認**。

### 🛑 欄位編碼（第一次解一定會踩到）

```
raw ... 0F C2 73 09 08 02 0E 07 00 ...
         Year =0x73=115  → 民國115年 = 西元 2026     ← 民國年,不是西元也不是 2000 offset
         Month=0x09=9    Day=0x08=8
         Week =0x02=2    → 週二                       ← 1~7
         Hour =0x0E=14   Min=0x07=7   Sec=0x00=0     ← binary,不是 BCD
```

**當成 BCD 會錯 6 個多小時**（`0x14` 讀成 14 而不是 20）。
**年份當成 2000+ 會解出「20115 年」。** 兩個都實際踩過。

## 設計

### A. 即時對時（人工，按鈕）

流程刻意做成**查 → 比 → 送 → 記**，不是盲送：

```
1. 送 0F42           查控制器現在幾點
2. 收 0FC2           解出控制器時間,與我方時間相減得「校正前差值」
3. 顯示確認框         我方時間 / 控制器時間 / 差值 / 要送的碼框
4. 送 0F12           帶我方當下時間
5. 收 0F92           取 SecDif —— 控制器自己認的差值
6. 記錄              兩個差值都存(我方算的、控制器回的),事後可交叉查核
```

沿用既有兩段式 `prepare` → `send`，過 `_control_guard` 四道把關，寫操作紀錄。
確認框顯示實際碼框與目標位址（與遠端重開機同一套）。

### B. 定時對時（自動，預設關閉）

🛑 專案規範：**自動行為必須對應使用者設定 toggle，不可 hardcode。**

```
每 CHECK_INTERVAL（預設 1 小時）:
    查 0F42 → 收 0FC2 → 算差值 D
    |D| <  THRESHOLD (預設 5 秒)   → 不動作,只記錄
    THRESHOLD ≤ |D| ≤ MAX_AUTO (預設 60 秒) → 送 0F12 校正,記 SecDif
    |D| >  MAX_AUTO               → 🛑 不自動校正,只告警
```

**為什麼要有 `MAX_AUTO` 上限**：差距過大代表控制器時鐘可能故障或被人改過，
那要人來判斷。自動把它拉一大步反而危險（見下）。

參數全部可設、持久化（沿用 `signal_conn.json` 那套，重啟維持）。

### ⚠ 風險：時間會影響時制計畫的時段切換

號誌控制器依**時間**查表決定跑哪一組時制計畫。若對時讓它跳一大步，
可能在**時段邊界**造成非預期的計畫切換（例如 06:59:50 跳到 07:00:10，
直接切進尖峰計畫）。

因應：

- `MAX_AUTO` 上限，差太多只告警不自動改
- 差值小時（< THRESHOLD）不動作，避免頻繁微調
- 自動校正**避開時段邊界前後數分鐘**（時段表來自 `ramp_timing_baseline.json` 的 `schedule`）
- 每次校正都寫入 `adjust-log`，事後查得到「那次計畫切換是不是對時造成的」

## API 設計（草案）

```
POST /api/signal/control/time-sync        即時對時(走 prepare→send,回 SecDif)
GET  /api/signal/time                     控制器時間 / 我方時間 / 差值 / 上次對時
GET  /api/signal/time/history             漂移歷史(給畫面畫曲線)
POST /api/signal/control/time-auto        定時對時開關與參數(持久化)
     body: {enabled, interval_sec, threshold_sec, max_auto_sec}
```

## 資料

沿用 `signal_frames`（`0F12` / `0F92` / `0F42` / `0FC2` 都會被持久化）。
另存一張輕量對時紀錄：時間、我方算的差值、控制器回的 `SecDif`、
有沒有實際校正、觸發來源（人工／自動）。

漂移曲線的價值：**能證明控制器時鐘穩不穩**。若發現規律性漂移（例如每天慢 3 秒），
那是硬體問題的早期訊號，可以在它影響時制之前先反映給機關。

## 分期

| 期 | 內容 | 風險 |
|---|---|---|
| 1 | `GET /time`：查 `0F42`、解 `0FC2`、顯示差值 | 唯讀，無 |
| 2 | 即時對時按鈕：`0F12` + `0F92`，含確認框與紀錄 | 低（設定類，但只改時鐘） |
| 3 | 漂移歷史與曲線 | 唯讀，無 |
| 4 | 定時對時（預設關閉，含門檻與上限保護、避開時段邊界） | 中（自動改控制器） |

**建議先做 1 + 3**：純唯讀，先累積兩週漂移數據，再決定 4 的門檻要設多少。
沒有數據就訂門檻是拍腦袋。
