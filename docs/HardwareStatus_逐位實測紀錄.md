**站點**：國道8號新市交流道（東向）`SIG-N8-E-9-L-E-1`
**目的**：不靠推論，逐一把每個位元送上中央，記下中央顯示什麼。
**工具**：`scripts/hwstatus_bit_probe.py`（每輪自動寫 `docs/reports/hwstatus_bit_probe.jsonl`）

## 這個欄位在封包裡的哪裡（2026-09-09 13:11 定位）

`eq_hw_status` 的**唯一**來源是 `0F04` / `0FC1` 的 HardwareStatus 兩個位元組。
近一小時控制器送出的所有碼（`5F03`/`0F80`/`0FC1`/`5FC8`/`5FC0`/`0F04`/`5F0C`/
`5FCC`/`0FC2`/`0F92`）掃過，沒有第二個訊息帶硬體狀態。

```
中央 0F41(設備硬體狀態－查詢，每分鐘)
  → 控制器 0FC1: AA BB 7C FF FF 00 0E 0F C1 [60 00] AA CC AB
                                       offset 9,10 ↑
  → 我方依模式改寫 offset 9,10 → 重算 CKS + byte stuffing → 送中央
  → 中央 1 分鐘週期產生 scmXMLData.xmL 的 eq_hw_status
控制器另外每分鐘自發一則 0F04，同樣位置。
```

**中央是把 offset 9（第一個位元組）直接當成 bit0~bit7、offset 10 當 bit8~bit15。**
我方相反（offset 9 是高位元組）。所以同一個 `0x40`：

| 讀法 | 值 | 位元 | 名稱 |
|---|---|---|---|
| 我方（big-endian） | `0x4000` | bit14 | `controllerReady` 控制器就緒 |
| 中央 | `0x0040` | bit6 | `signalDriverUnitError` 號誌驅動單元錯誤 |

控制器原始的 `60 00` 在中央眼裡就是 bit5+bit6 = `I/O unit error` +
`SIGNAL_DRIVER_UNIT_ERROR` —— 正是切 `raw` 時中央跳的那兩條。

## 量測方法（每一位都照這個流程）

1. `POST /api/signal/control/hwstatus-mode?mode=force&value=<值>&mask=0`
   （`force` **不落檔**，重啟自動回到設定檔的 `swap`）
2. 從 `signal_frames.sent_hw` 確認**真的有一框帶著這個值上線路**，記下時間
   —— 只看 API 回應不算數，值要真的出現在線路上。
3. 等中央那份 XML **換過兩個週期**再讀（保險，不是每次都要）。
   🛑 中央的 XML 是**整分產生的快照**，值要在整分前**夠早**上線路才會進得去：
   · bit14：13:54 上線路（整分前 6 秒）→ 14:00 那筆**沒有**，15:00 才出現
   · bit13：33:20 上線路（整分前 40 秒）→ 34:00 那筆**就有了**
   所以延遲是 6~66 秒不等，取決於落在一分鐘的哪個位置。等兩個週期一定安全。
4. 記 `eq_hw_status`（腳本自動抓）＋ 中央畫面的「硬體狀態」燈號（**只能現場人工回報**，
   它是另一條解析路徑，XML 裡沒有這個欄位）。

## 燈號（硬體狀態）的判準 — 三點實測

燈號是**另一條路徑**，XML 裡沒有這個欄位，只能由現場看畫面。

| 送出 | byte0 | byte0 的 bit6 | 告警欄 | 燈號 |
|---|---|---|---|---|
| `0x4000` | `40` | **1** | `SIGNAL_DRIVER_UNIT_ERROR` | **綠（正常）** |
| `0x0040` | `00` | 0 | 空 | **紅（異常）** |
| `0x0400` | `04` | 0 | `計時器異常` | **紅（異常）** |

**燈號只看 byte0 的 bit6，與有沒有告警無關**（`0x0040` 沒告警也是紅、
`0x0400` 有告警也是紅）。而 byte0 的 bit6 **同時就是**中央告警表的 bit6
`SIGNAL_DRIVER_UNIT_ERROR`。

→ **就緒燈與號誌驅動單元錯誤是同一個位元。設 1 得到綠燈＋假告警，
設 0 得到無告警＋紅燈。我方無論送什麼值都不可能同時滿足。**

## 🛑 這份紀錄證明了什麼、沒證明什麼

**證明了（實測）**：我方在 offset 9/10 放某個位元 → 中央顯示哪一個名稱。
也就是**位元組順序**與**中央的位元→名稱對照**。這一半每一筆都有時間戳。

**沒有證明（抄協定）**：下表「我方語意」那一欄的名稱。它來自協定 4-36 的
**建議**位元表（`HW_BITS` 的 `evidence=spec`），而協定 4-36 自己就寫著
「各位元為建議及參考內容，主辦機關可依需求修訂」。

10 天 45,843 筆抄錄裡，**只有 bit2 / bit13 / bit14 曾經為 1**，其餘 13 位
一次都沒亮過 —— 所以「控制器真的發生該項故障時會把那一位設 1」這件事，
除了下面三位之外**全部未經驗證**：

| 位元 | 我方語意的證據 |
|---|---|
| bit14 控制器就緒 | 運轉中恆為 1，十天無維修紀錄 → 站得住 |
| bit13 外部時相控制進行中 | 與 `5F10` 控制策略 bit4 比對 45,843 筆一致率 95.8% → 站得住 |
| bit9 機箱門開啟 | 我方電子鎖門磁實測對照 → 站得住 |
| bit1 / bit5 / bit6 / bit2 / 其餘 | **只是抄協定，未驗證** |

🛑 **做書面說明時只能主張位元組順序，不能主張名稱。**
「我方 bit1 = 記憶體錯誤」若被中央端反問「你怎麼確定」，我方答不出來。
能主張的是：「同一個位元組，貴端讀成 bit0~7、我方讀成 bit8~15，
三對六個方向實測全部吻合。」

## 到目前為止的結論（四筆實測，四次預測全中）

| 我方送 | 我方語意（⚠️ 多數只是抄協定） | 中央顯示（✅ 實測） | 中央讀成 |
|---|---|---|---|
| `0x4000` bit14 | 控制器就緒 | `SIGNAL_DRIVER_UNIT_ERROR` | bit6 |
| `0x2000` bit13 | 外部時相控制進行中 | `I/O unit error` | bit5 |
| `0x0020` bit5 | I/O 單元錯誤 | `TIMMING_PLAN_ON_TRANSITION` | bit13 |
| `0x0040` bit6 | 號誌驅動單元錯誤 | （空，錯誤表無 bit14） | bit14 |
| `0x0200` bit9 | 機箱門開啟 | `記憶體異常` | bit1 |
| `0x0002` bit1 | 記憶體錯誤 | `CABINATE_OPENDED` | bit9 |

**中央把 HardwareStatus 的第一個位元組直接當成 bit0~bit7、第二個當 bit8~bit15；
我方相反。** bit13↔bit5、bit14↔bit6、bit9↔bit1 **三對互為反讀，六個方向全部測到**，
不是巧合，也不是「中央有一張不同的錯誤表」——是**位元組順序**。

順帶一提，中央的告警名稱是中英混雜的（`記憶體異常` 是中文，其餘是英文代碼），
且 `CABINATE_OPENDED` 兩個字都拼錯 —— 那是中央端的字串原文，不是我方轉錄錯誤。

### 🛑 最硬的一條：中央的「就緒」與 `SIGNAL_DRIVER_UNIT_ERROR` 是**同一個實體位元**

把四筆併起來看，比「位元組順序」更致命的事情浮出來了：

```
封包 offset 9 這一個位元組:   0 1 0 0 0 0 0 0     ← 值為 0x40 時
                                 ↑
              我方叫它 bit14 controllerReady（它是我方高位元組的 bit6）
              中央叫它 bit6  signalDriverUnitError（中央把這個位元組當 bit0~7）
```

不是「兩條路徑讀同一個欄位但順序不同」——是**同一個位元被賦予兩種相反的意義**：

| offset 9 的 bit6 | 中央硬體狀態燈 | 中央告警欄 | 實測 |
|---|---|---|---|
| **1**（送 `40 00`） | **綠色／正常** | `SIGNAL_DRIVER_UNIT_ERROR`（假的） | ✅ 09-09 13:58 燈號、14:01 XML |
| **0**（送 `00 40`） | **紅色／異常** | 空 | ✅ 09-09 13:38 起 |

**四個角全部由現場畫面確認，沒有一格是推論。**

**所以「為什麼沒有第三種選擇」有了更直接的答案**：不是找不到對的值，是
**這一個位元不可能同時是 1 和 0**。`0x4040` 也救不了 —— 告警只看 offset 9
那個位元組，它照樣會是 `SIGNAL_DRIVER_UNIT_ERROR`。

這條**只能中央端改**，我方沒有任何值可以繞過去。
