# 降階運轉與故障檢核 — 規劃

對應規範 R34-16613 的 **(D) 降階運轉**、**(E) 故障檢核與統計**、**(G) 員警手動與時相綁定**。
2026-09-07 建立。目前系統為「線上評估」（通訊已接上、控制未下發），本文規劃的是
**接管（L5）之後**必須先具備的安全機制；在接管之前，其中的偵測與統計部分可以先做。

---

## 零、一個關鍵實測，決定了整個設計方向

2026-09-07 現場觀測到：

```
10:20:48  外部系統最後一筆 5F1C
10:25:48  控制器自己回到內建定時控制（5FC0 策略 0x01）
```

中間沒有任何人下「請回復固定時制」的命令 —— 那是 **`5F10` 的 EffectTime 看門狗到期**
（設定 5 分鐘，不續約就失效）。

**這代表我方的降階可以做成 fail-stop：只要停止下發，控制器會自己回到固定時制。**
不需要在故障當下再送一則命令（那時候正是最不該相信自己還能正確送命令的時刻）。

> 🛑 這一點必須在接管前用**現場實測**再確認一次，並記錄 EffectTime 的實際設定值。
> 整份降階設計都建立在它上面；如果控制器不是這樣行為，(D)(E) 全部要重做。

## 一、單元切分與相依（(D) 的前提）

要談「單一單元故障不影響其他單元」，得先講清楚有哪些單元。

| # | 單元 | 行程 | 失效會影響 |
|---|------|------|-----------|
| U1 | 相機影像 ×4 | Frigate / go2rtc | U2 |
| U2 | 壅塞偵測（佔有率、排隊、流量） | traffic-api 內執行緒 | U3 |
| U3 | 決策引擎（四道閘門 + 延滯比較） | traffic-api 內 | U4 |
| U4 | 號控下傳（5F1C / 5F10 續約） | traffic-api 內 | 路口號誌 |
| U5 | 抄錄器（5F03/5F00…解碼） | traffic-signal（獨立行程） | U3 的燈態輸入、U6 |
| U6 | 中央中繼（中央 ↔ 控制器） | traffic-signal 內 | 中央看得到的一切 |
| U7 | 電子鎖 / IO | traffic-io（獨立行程） | 機箱狀態上傳 |

**已經成立的隔離**（不是規劃，是現況）：

- U5/U6 與 U7 是**獨立 systemd 服務**，traffic-api 重啟不會斷抄錄與中央中繼
- U1 失效時該側視為「未量到」（0 車），不會製造假需求
- U6 是純轉發，不依賴 U2/U3 的任何結果

**還沒成立的**：

- 🛑 U4 目前與 U2/U3 同行程。U2 卡住（例如相機 I/O 阻塞）會讓 U3 停止更新，
  而 U4 若還在續約 `5F10`，控制器會一直停在外部控制、吃著一份**過期的決策**。
  這是 (D) 最實際的風險，解法見第二節。

## 二、降階矩陣（(D)）

「降階」不是二元的開/關，要分級。以下四級，級數越高我方介入越少。

| 級 | 觸發 | 我方行為 | 路口結果 |
|---|------|---------|---------|
| **L0 正常** | 全部單元健康 | 正常下發 5F1C，5F10 續約 | 動態控制 |
| **L1 降級控制** | 單台相機失效 / 單側量測不可用 | 該側視為 0 車，**仍下發**但只用可信的一側 | 動態控制（保守） |
| **L2 停止下發** | U2 或 U3 逾時、決策過期、指令傳輸錯誤 | **停止 5F10 續約**，不再送 5F1C | 看門狗到期後自動回固定時制 |
| **L3 全退出** | U5 抄錄中斷（拿不到燈態）/ 我方行程異常 | 同 L2，並停止一切對控制器的寫入 | 固定時制 |

🛑 **L2 與 L3 的動作刻意相同：什麼都不做。**
故障當下最不該做的事，就是再送一則命令去「處理」故障。

### 判定條件（要可量測、可稽核）

| 條件 | 量測方式 | 門檻（初值，需現場調） |
|---|---|---|
| 決策過期 | 最後一次成功決策距今秒數 | > 3 個決策週期 |
| 量測過期 | 該相機最後一筆壅塞結果距今 | > 10 秒 |
| 燈態過期 | 最後一框 5F03 距今 | > 40 秒（現況中位 3.1 秒、最大 36.8 秒） |
| 指令傳輸錯誤 | 5F1C 送出後未收到 0F80 ACK | 連續 2 次 |
| 上游連線 | recorder `connected` / `age_sec` | 斷線即 L3 |

> 🛑 門檻不可以憑感覺定。上表的初值取自 2026-09-07 的實測分布，
> 上線前要用至少一週的資料重算 p99，並把依據寫進上線報告。

## 三、故障檢核與回報中心（(E)）

### 3.1 三類故障，規範明列

| 規範說的 | 我方對應 | 偵測 |
|---|---|---|
| 偵測器發生故障 | U1/U2 | 量測過期、相機離線、壅塞執行緒不在 |
| 運算邏輯錯誤 | U3 | 決策過期、例外、輸出超出合理範圍（如綠燈建議 > 最大綠） |
| 指令傳輸錯誤 | U4/U5 | 送出無 ACK、上游斷線、CKS 錯誤率上升 |

### 3.2 回復固定時制

依第零節：**停止續約即可**。實作上要有一支明確的
`enter_degraded(level, reason)`，做三件事且只做三件事：

1. 設旗標，讓下發路徑一律拒絕（與 `_control_guard` 同層，不是靠呼叫端自律）
2. 寫一筆故障事件（時間、級數、觸發條件、當下量測值）
3. 觸發回報（見 3.3）

🛑 **不要在降階時送任何 TC3 命令。** 包含「送 5F15 切回固定時制」——
那要求「我方仍能正確下發」，但降階的前提正是「我方可能不能」。

### 3.3 回報中心 — **這一條需要與機關確認做法**

規範要「將故障訊息回傳中心」，但 TC3 是**號誌控制器與中心**之間的協定，
沒有「策略軟體故障」這種由中繼方發出的訊息。我方目前是中繼，能做的有三條路：

| 做法 | 優點 | 缺點 |
|---|---|---|
| A. 靠控制器自己回報 | 不竄改任何東西。控制器策略從 0x10 變回 0x01 會發 `5F00`，中心看得到 | 中心只知道「外部控制停了」，不知道原因 |
| B. 我方以 `_send_to_center()` 發一則自訂訊息 | 能帶原因 | 🛑 TC3 沒有這個訊息碼，等於自創協定，中心不一定收 |
| C. 走既有的告警/報表通道（非 TC3） | 資訊完整、可附證據 | 不是「回傳中心」的字面意思 |

**建議 A + C**：控制器的策略回報是中心一定看得到的事實（不需我方誠信），
原因與證據走報表。B 不做 —— 自創協定訊息會變成另一個「只有我們自己相信」的東西。

> 待確認：機關認不認可「以控制器策略回報作為故障回傳」？（見驗收對照 §七）

### 3.4 遠端開關

現況：`SIGNAL_TC3_CONTROL` 與 `SIGNAL_TC3_CONTROL_QUERY_ONLY` 兩個 env + 執行期
`hwstatus-mode` 的切換端點。要滿足 (E) 的「遠端開關」需要：

- 介面上一個明確的**總開關**（啟用/停用動態控制），狀態要能被查詢
- 🛑 開關必須落在**把關層**（`_control_guard`），不是介面層 —— 只擋按鈕的話，
  知道 API 的人照樣送得出去（今天 `QUERY_ONLY` 的設定與行為不一致，就是提醒）

## 四、統計補齊（(E) 後半）

規範明列要能查詢或產出：運作狀態、歷史時制調整紀錄、**調整次數、平均綠燈時間、
變異數**、執行績效、故障情形。

| 項目 | 現況 | 待補 |
|---|------|------|
| 運作狀態 | ✔ 運作統計分頁 | — |
| 歷史時制調整紀錄 | 部分（影子/評估 log 有決策，但沒有「調整」——因為還沒下發） | 接管後每次 5F1C 落一筆：時間、分相、步階、原因、當時量測 |
| 調整次數 | ✘ | 同上，依時段彙總 |
| 平均綠燈時間 | ✔ 有分布 | 補「平均」欄位（現在只有分布圖） |
| **變異數** | ✘ | 綠燈長度的變異數，依分相、依時段 |
| 執行績效 | 部分（線上評估） | 🛑 要帶「樣本鑑別力」，紅側沒車的時段不可當成效證據 |
| 故障情形 | ✘ | 降階事件表（3.2 的第 2 步就是資料來源） |

## 五、員警手動控制（(G) 前半）

抄錄器已能判讀控制模式（`5FC0` 策略位元 bit2 路口手動 / bit3 中央手動）。
規劃行為：

1. 偵測到 **bit2 路口手動** → 立即進入 **L2**（停止下發），並記錄
2. 🛑 **不要嘗試「配合」手動**：現場員警在處理的通常是我方看不到的狀況
   （事故、車隊、臨時管制）。此時演算法的最佳行為是**讓開**。
3. 手動解除後不立即恢復下發 —— 等 `5FC0` 連續 N 次回報非手動（去抖動），
   避免切換瞬間的位元跳動（實測 `5F10` 續約時策略位元會跳一秒）造成誤判
4. 手動期間的樣本要在評估時**排除**，理由與清道期間相同：那不是任何演算法的決策

## 六、基準方向與時相編號綁定（(G) 後半）

規範要求：時制參數中之基準方向與時相編號**綁定**，避免分開規劃的時間差導致
方向與時相錯置。

我方現況：時制表有 `phases` 與 `green_directions` 兩份資料，**沒有綁定檢核**。

規劃：

1. 綁定表以「時相編號 → 基準方向」為唯一真相，存成單一結構，不允許分開更新
2. 每次抄到 `5FC2`/`5FC5`（時相排列、時制計畫）就跑一致性檢核：
   - 時相編號有出現但沒有對應方向 → 標示不一致
   - 方向對應到不存在的時相編號 → 標示不一致
   - 與上次抄到的綁定不同 → **標示為變更**並保留兩版（現場改過的證據）
3. 檢核不通過時：**不阻擋抄錄**（那是唯讀的），但**阻擋下發** —— 綁定錯的時候
   送時相控制命令，正是規範要防的「方向及時相錯置」

> 🛑 現況阻礙：`5F42/5FC2` 最後一次抄到是 **14 天前**（見設定頁鮮度）。
> 綁定檢核要有意義，得先讓這幾項設定定期查回來。

## 七、實作順序（依「不需接管就能做」優先）

| # | 項目 | 需要接管? | 備註 |
|---|------|:---:|------|
| 1 | 降階事件表 + `enter_degraded()` 骨架 | 否 | 先能記錄，接管後才生效 |
| 2 | 判定條件的量測與門檻（用一週資料算 p99） | 否 | 純觀測 |
| 3 | 統計補：平均綠燈時間、變異數、調整次數欄位 | 否 | 調整次數在接管前恆為 0，欄位先備好 |
| 4 | 基準方向 × 時相編號綁定檢核 | 否 | 先讓 5F42 定期查回來 |
| 5 | 手動控制 → L2 的行為與去抖動 | 否 | 現在就能記錄「若有下發會被擋」 |
| 6 | 控制總開關落到把關層 | 否 | 順便修 QUERY_ONLY 設定與行為不一致 |
| 7 | EffectTime 看門狗行為現場實測確認 | 是（需下發一次） | **整份設計的前提** |
| 8 | 回報中心的做法與機關確認 | 否 | 見 3.3 |

## 八、要與機關確認

1. **故障回傳中心的形式**：接受「以控制器策略回報（`5F00`）作為故障已回傳」嗎？
   還是要求我方自行發出訊息（TC3 無此訊息碼）？
2. **降階級數的定義**：本文的 L0~L3 是否符合「降階運轉」的認定？
3. **統計的呈現位置**：介面查詢即可，還是需要可匯出的定期報表？
4. **員警手動時的期待**：規範說「調整動態號誌控制策略」——我方的解讀是
   **完全讓開**（停止下發）。若機關期待的是「配合手動做局部調整」，
   那是完全不同的設計，要及早確認。
