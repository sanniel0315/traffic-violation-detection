## 三、岐異是「單向」的 —— 我方一律比 OPAC 早切

1,074 筆岐異**全部**是「我方要切、OPAC 續綠」。

尖峰時段紅側排隊已 ≥50 m 卻仍被 OPAC 續綠：**122 筆**。

## 四、根因：我方 keep_gain（綠側價值）幾乎恆為 0

岐異的 1,082 筆裡，**724 筆（67%）的 `keep_gain = 0`**。
典型 reason 字串：

```
紅側延滯 744 > 綠側價值 0 + 換相成本 12
```

`change_cost` 固定 12.5，相對於數百的紅側延滯根本擋不住。
所以只要紅側有排隊、綠側量到 0，模型必然喊 SWITCH。

**問題出在「綠側價值」的定義**：我方用的是**當下靜態排隊公尺**，
車一放行排隊就歸零，模型立刻認為「綠燈已經沒價值」——
但實際上綠燈期間**車流仍在持續到達並被消化**，那才是綠燈的價值。

對照 OPAC 的 `pn2`（綠側未消化放行需求）：它是**隨綠燈遞減的狀態量**，
不是瞬時排隊。這正是我方模型缺的那一項。

**修正方向**：`keep_gain` 要改成「排隊 + 綠燈期間的到達流量 × 剩餘服務時間」，
把 `congestion_detector` 已經在算的 flow (vpm) 納進來，而不是只看 queue_m。

## 六、順帶發現：OPAC 綠燈曾超過官方最大綠

`green_elapsed` 最大值：分相1 = 254.7s、分相2 = **433.3s**。
超過 210s（官方時制表最大綠）的樣本 54 筆，集中在 **04 時（45 筆）與 06 時（9 筆）**。

離峰無車時長綠不影響通行，但這代表 OPAC 的續綠**沒有受官方 max-green 拘束**
（先前記錄的 OPAC 內部 max-green=100 也對不上）。此點建議向中心端確認。
