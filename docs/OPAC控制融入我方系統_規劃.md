> **終局目標：bypass OPAC —— 我方自己做動態號誌控制。**
> 中途目標：兩者並行運作，我方先「看得見、算得出、比得了」，驗證成熟後接手控制權。
> 建立：2026-09-02。前提事實見 `OPAC匝道整合_紀錄.md`、`OPAC控制監控_實時log.md`。

## 〇、終局與路徑

```
現在          →  並行期(本規劃)        →  終局
OPAC 控制        OPAC 控制 + 我方影子     我方控制(bypass OPAC)
我方只供資料      我方算出自己的決策並比對   OPAC 可停用或當備援
```

**為什麼可行**：我方已具備 OPAC 的**全部三項要素** ——
①偵測(排隊/流量) ②官方時制基準(查表層) ③TC3 下發通道(signal_tc3 control/send)。
缺的只有「決策引擎」與「呈現/比對介面」,而 OPAC 的演算法邏輯今日已完全反推出來
(`pn1>pn2` 切換、pn1=紅側累積需求、pn2=綠側未消化殘量)。

**並行的價值**:OPAC 在跑的期間,我方影子決策可與它逐筆比對 ——
這是驗證我方演算法正確性的最佳時機,零風險(影子不下發)。

## 三、融入方案（三層，由淺到深）

### 🟢 L1：控制模式標示（最小改動，價值最高）

**我方已經解出 `strategy` 位元，只要加上語意判讀即可。**

在「號誌燈態」頁的路口卡上加一個狀態標籤：

| 控制器 strategy 位元 | 顯示 | 顏色 |
|---|---|---|
| `phase=1`（bit4 時相控制） | **動態控制中（OPAC）** | 綠/強調 |
| `fixTime=1, phase=0` | 定時控制（計畫 N） | 藍 |
| `roadSideManual=1` 且 `phase=0` | 路側手動 | 橘（警示） |
| 其他/異常 | 依 `_strategy_text()` 原樣顯示 | 灰 |

> 🛑 判讀重點（今日實證）：`roadSideManual=1` 在 OPAC 接管期間**也會是 1**
> （OPAC takeover-strategy 寫入），所以**不能只看 roadSideManual 就說是手動**，
> 必須搭配 `phase` 判斷。這正是本次測試中造成誤判的點。

**實作**：`signal_tc3.py` 的 `/status` 或 `/safety` 多回一個 `control_mode`
欄位（`opac_dynamic` / `fixtime` / `roadside_manual` / `unknown`），前端路口卡加標籤。
**成本低、不需碰中心端。**

### 🟡 L2：控制事件時間軸

把「控制權變化」做成可追溯的事件流 —— 我方安全網已經在記策略變更事件，
只要補上語意與呈現：

- OPAC 接管 / 交還（`phase` 0↔1 的變化）
- 回退到定時（死人開關生效）
- 策略被打回（今日觀察到 3 次）

**價值**：本次測試中「控制權被奪回 3 次」就是靠中心端 log 才發現的。
若我方安全網把這個變成事件+推播，**不用進中心端就能第一時間知道**。

**實作**：`_safety_watch` 已有邊緣觸發機制（值改變才記事件），
只要把 `phase` bit 的變化獨立成一類事件（目前是整包 strategy 變化）。

### 🔵 L3：決策脈絡對照（完整融入）

把「我方排隊資料」與「號誌實際反應」並排，回答
**「我們餵的資料造成了什麼控制結果」**：

```
時間      我方排隊(NE-2/WN-2)   控制器分相   綠燈秒數   判讀
15:22:30      2台 / 11台          分相2        100s      下匝道塞→長綠(撞上限)
15:45:02      1台 /  1台          分相1         15s      兩邊都少→快速輪替
```

資料兩邊都有（排隊來自 `congestion_detector`、分相/秒數來自 `signal_tc3` 抄錄），
**只需在同一個時間軸上對齊呈現**。

**價值**：這是驗證「動態號誌是否真的有效」的唯一方法 ——
排隊變多時綠燈有沒有變長？切換是否合理？

**選配**：若中心端願意開放 OPAC 的 `/api/opac/status` 或 MQTT `tcis/opac`
給我方訂閱，可再疊上 `pn1/pn2`、`dataMode`、下發成功率等中心端指標。
但**沒有這些也能做 L3**，因為輸入(排隊)與輸出(燈態)我方都看得到。

### 🟣 L4：我方影子決策引擎（bypass 的前置，零風險）

**在 OPAC 還在控制時，我方同步算出「如果是我，我會怎麼切」，只記錄不下發。**

輸入我方全部都有：
```
排隊/流量      congestion_detector (queueM、stopped、flow)
官方時制基準   signal_timing_lookup (計畫/min·max green/儲車上限/主線保護優先)
即時燈態相位   signal_tc3 抄錄的 5F03
```

決策邏輯直接對照今日反推出來的 OPAC 規則（已完全掌握）：
```
pn1 = 紅燈側累積等待需求      pn2 = 綠燈側未消化放行需求(隨綠燈遞減)
SWITCH ⟺ pn1 > pn2           守 min-green,主線保護優先(分相2 下匝道)
```

**比對介面**（這是 L4 的產出）：
```
時間      OPAC決策    我方影子決策   一致?   我方排隊(NE/WN)
15:45:02  SWITCH      SWITCH         ✅      1台 / 1台
15:45:27  KEEP        SWITCH         ❌      2台 / 5台   ← 差異點,要檢討
```

**價值**：這是**唯一能在零風險下驗證我方演算法**的方式。
OPAC 是現成的「標準答案」，我方影子跑得夠久、一致率夠高，才有底氣 bypass。

### 🔴 L5：接管控制（bypass OPAC）

前置條件（缺一不可）：
1. L4 影子決策與 OPAC 一致率達標（建議連續數日 >95%，差異點都能解釋）
2. 我方下發通道驗證過（`signal_tc3` 的 `control/prepare` + `control/send`，
   目前 `SIGNAL_TC3_CONTROL=1` 未開、且有 `QUERY_ONLY` 雙保險）
3. **接管/交還機制對齊 OPAC 的安全設計**：
   - 5F10 effectTime 續約（死人開關）—— 我方掛掉也要自動回定時
   - 資料失聯降級（≥30s 走固定綠）
   - min/max green 硬邊界、主線保護不可違反
4. 中心端停用 OPAC（`kubectl scale --replicas=0`），避免兩邊搶控制權

**切換方式**：OPAC 停用 → 我方送 5F10 接管（讀當下綠燈方向續接，不跳燈）
→ 我方每 60 秒續約 → 我方逐步階下 5F1C。

> 🛑 **我方 TC3 下發預設關閉是刻意的**（`signal_tc3.py` 開頭紅字警告：
> 送錯一則 5F15/5F10 會直接改變路口實際運轉）。L5 才解除，且要分階段：
> 先影子 → 再人工確認下發 → 再受限自動 → 最後全自動。

## 四、建議順序與理由

| 階段 | 內容 | 依賴 | 價值 |
|---|---|---|---|
| **L1** | 控制模式標示 | 無（純我方） | 立刻消除「是不是被切手動」的誤判 |
| **L2** | 控制權事件+推播 | 無（純我方） | 控制權被奪回時第一時間知道 |
| **L3** | 排隊↔配時對照 | 無（純我方） | 驗證動態控制成效 |
| L3+ | 疊中心端 OPAC 指標 | 需中心端開放 | 錦上添花 |
| **L4** | **影子決策引擎 + 一致率比對** | 無（純我方） | **bypass 的前置驗證，零風險** |
| **L5** | **接管控制（bypass OPAC）** | L4 達標 + 中心端停 OPAC | **終局** |

**L1~L4 都不需要中心端配合**，因為我方抄錄的 5F03 與 icagent 同源、
且影子決策不下發。只有 L5 需要中心端停用 OPAC 以免搶控制權。

**⚡ 關鍵時機**：OPAC 現在正在跑 = L4 影子比對的最佳窗口。
OPAC 是現成標準答案，錯過這段就沒有對照組了。建議 L1~L2 先做（快、
立刻解決判讀誤導），同時盡早啟動 L4 蒐集比對資料。
