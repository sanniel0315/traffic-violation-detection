# 號誌管理功能對照與實作計畫

> 目標：`/sig`（10.42.38.35）那套號誌控制管理的功能，**我方系統要全部具備**。
> 建立：2026-09-03。前提事實見 `號誌整合_功能缺口分析.md`、`中央查詢指令盤點.md`。

## 〇、先講兩件影響判斷的事

**1. `/sig` 的多數頁面是展示資料，不是真的接上了。**
它的 i18n 字串裡到處是「目前為展示資料，暫停用」、「即時更新需後端服務」、
「匯出需後端服務」。運作統計頁還寫著
`本路口尚未設定號誌統計資訊對照 … 未設定前本頁無資料來源`。
所以那是**功能規格書**，不是可對照的運轉基準。

**2. 我方的資料源比它完整。**
`_decode_fields()` 走 `utc-tc3` 函式庫，**已能解出任一 TC3 訊息的欄位表**。
我方又同時握有：5F03 逐秒燈態抄錄、自家的排隊/流量量測、影子決策紀錄。
缺的多半只是「查回來 + 攤成表」，不是解不出來。

## 二、本次已完成

### 2.1 運作統計 `/api/signal/shadow/stats`

從影子 5 秒取樣**重建每一次綠燈的實際長度**，再據以統計：

| 指標 | 說明 |
|---|---|
| 相位切換次數 | 區間內綠燈段數 − 1（非累計值） |
| 強制切換次數 / 佔比 | 段內出現 max-green 強制的次數 |
| 綠燈時間統計（依方向） | 樣本數 / 平均 / **變異數 / 標準差** / 觀測最小最大 |
| 綠燈秒數趨勢 | 逐段長度 + 強制切換標記 |
| 出口滯留 | 下匝道（分相2）排隊公尺與換算車輛的平均與最大 |

重建方式：同一分相內 `green_elapsed` 遞增，**一旦變小就是換相**。
這比比對 `sub_phase_id` 穩，因為分相在 1/2 之間來回，單看編號分不出
「同一個分相的第二輪」。

> 🛑 三個誠實標註：
> ① 每段取最後一筆取樣的秒數，**最多低估一個取樣週期（5 秒）**。
> ② 抄錄過期（stale）被跳過的取樣會讓該段斷開。
> ③ 區間內第一段的起點在區間之前，長度不完整，**不列入統計**。
> ④ 查無樣本各指標回 `null` 並附 `insufficient_data` ——
>    **不以 0 代表統計值**。0 次切換和「沒有資料」是完全不同的兩件事。
>    （這條是從 `/sig` 的 `資料不足：… 未以 0 代表實際統計` 學來的，值得抄。）

### 2.2 號誌設定總覽 `/api/signal/config`

一個唯讀端點涵蓋 11 個設定類別（控制策略／時制計畫／時相排列／一般日與
特殊日時段型態／觸動控制／傳輸週期／VIP／硬體狀態／韌體版本／日期時間），
每項回傳最新回報時刻 + `utc-tc3` 解出的欄位表。

> 🛑 純唯讀：只讀已抄錄到的回報框，不送查詢也不下設定。
> 沒抄到就明講「尚未收到」並附上該用哪個查詢碼，
> **不回空表假裝控制器沒設定** —— 那是兩件完全不同的事。

## 三、後續順序（由高價值到低）

| 順序 | 項目 | 理由 |
|---|---|---|
| 1 | 前端「號誌設定」頁（吃 `/config`） | 一頁涵蓋 6 個缺的設定類別，投報比最高 |
| 2 | 前端「運作統計」頁（吃 `/stats`） | 後端已好，只差呈現 |
| 3 | 補送查詢：`5F42` 時相排列 | 唯一完全沒抄到的類別，要擴 `_run_self_probe` |
| 4 | 設備狀態頁（`0FC1` HardwareStatus 分組解讀） | 現場維運直接受益 |
| 5 | 時間偏差總覽 | 需先確認控制器時間的取得方式（`0F52`/`0FD2`） |
| 6 | 異動紀錄分類 + 回讀現值 | 安全網已有事件，補分類與回讀 |
| 7 | 設備組態（多路口） | 目前只有一個路口，需求不急 |

## 四、不做的事

**不做設定下發介面。** `/sig` 有「控制策略/時制計畫」的設定功能，
我方 `SIGNAL_TC3_CONTROL` 預設關閉且有 `QUERY_ONLY` 雙保險，
這是刻意的（`signal_tc3.py` 開頭紅字：送錯一則 5F15/5F10 會直接改變路口實際運轉）。
下發只在 bypass OPAC 的 L5 階段開放，且要分階段：
先影子 → 再人工確認下發 → 再受限自動 → 最後全自動。
